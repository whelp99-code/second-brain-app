# P05 — 타임라인·엔터티·관계

명세 등록 / 구현·시험 NOT_RUN. Refs #3. 선행 P02 #6, P03 #7. R1 / REQ-02·REQ-06·REQ-09 / Core+Client / 5–7인일 추정. 기준: 개발계획 4·6·12·16.1장. 원문 식별/hash는 #3.

## 목표
하루를 사건과 근거 중심으로 재구성하되 기록 수집 범위를 하루 전체로 과장하지 않는다. 관계 그래프는 날짜 근접이나 이름 일치만으로 사실을 만들어내지 않는다.

## 화면과 조회 계약
하루 화면에는 날짜/시간대, 마지막 수집 시각, 출처별 freshness/covered_window, 사건 목록, 결정 변화, 미확인, 원문 링크가 필요하다. 사건 카드에는 시간·시간 정밀도·제목·예정/실제/취소·관측/추정/사용자 발언·인물/프로젝트·근거 수·정정 동작이 있다. 모르는 발생 시각은 undated/range로 표시한다.

## 구현 체크리스트
- [ ] frozen 사건 snapshot에서 결정적으로 timeline을 생성하고 조회 I/O와 순수 집계 함수를 분리한다.
- [ ] KST 사용자 날짜→UTC 반열린 구간으로 조회한다. 자정을 넘는 사건, 여행 시간대, 동률 ID 정렬, 페이지 cursor와 generation을 처리한다.
- [ ] 일정·메일·메모의 같은 사건 후보를 묶되 모든 원출처와 개정/인용을 보존한다. 시간 근접만으로 확정 병합하지 않는다.
- [ ] 사람·회사·프로젝트·장소·사건·결정의 안정 ID/alias를 관리하고 동명이인의 분리/병합 정정을 되돌릴 수 있게 한다.
- [ ] participated_in/works_on/located_at/supports/contradicts/supersedes를 허용 목록으로 관리한다. relation마다 evidence·유효기간·추정 여부를 저장한다.
- [ ] 미검증 관계는 확정 그래프와 분리하고 LLM 후보 생성은 P10 통과 후 연결한다. R1은 규칙/명시 근거 기반 관계부터 가능하다.
- [ ] 제목·노드 수·연결 자체·근거까지 scope를 검사한다. 정정/삭제 후 관련 타임라인·관계를 동일 게시 세대에서 재생성한다.
- [ ] 기존 API에 timeline/event detail의 버전형 route를 추가하고 P06용 projection 입력을 제공한다.

## 코드·성능
신규 후보 `sb/life_timeline.py`, 작은 entity/relation helper와 기존 web 조회 경로. `sb/vault.py`의 단일 writer 및 기존 ledger를 재사용한다. 새 그래프 DB/Node API는 제외한다. 초기 성능 목표는 10만 사건·동시조회3의 지정 서버에서 timeline p95≤1초이며 P00 측정 후 조정한다. 현재 측정값이 아니다.
