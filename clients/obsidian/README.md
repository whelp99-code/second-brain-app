# Second Brain Memory Browser

A small Obsidian client for the existing Python Second Brain server. It manages a dedicated human-readable View Vault, not the core Vault or canonical DB.

## Implemented client paths

The plugin provides session login, verified paged synchronization, memory home, date navigation, capture, explicit personal-note capture, current/as-of recall, evidence inspection, correction, question response/skip/mute, typed-relation filters, prediction/actual views, and source/delivery/device status. The command IDs are registered in `main.src.cjs` and tested by `test/paging-ui.test.cjs`.

`Auto/` is server-managed; `MyNotes/` remains user-owned. Unknown existing files are not adopted. Changes to a previously managed file become conflicts, never silent overwrites. The synchronization journal records intended hashes before compare-and-write and only advances the cursor for a complete, conflict-free snapshot. Pages from different generations cannot be combined. Full generation and file hashes are verified before writes.

Withdrawn unchanged managed files become withdrawal placeholders. This does not promise physical deletion of user edits, local history, backups or disconnected devices. Original evidence is shown as plain text, not active HTML/Markdown; remote tracking images are not loaded.

## Authentication and installation

Use a dedicated View Vault with only this bridge writing `Auto/`. Do not connect the core managed Vault to a second synchronization writer. Install the built files under `.obsidian/plugins/second-brain-memory-browser/` using Obsidian's own plugin controls. Actual desktop/mobile installation is a separate acceptance test; it was not executed by a Node test.

The base URL must be HTTPS except for local loopback development. Configure an allowed source ID and a distinct life-only device credential. The plugin rejects an administrator credential kind. The token remains in session memory and is not saved in plugin data. The server also supports operator-configured, source-limited, expiring per-device credentials via `life_devices`, without creating a new authentication service.

The bridge pulls manually or on foreground return after login. It does not run continuously while iOS has closed Obsidian. It does not automatically sync all personal notes. Use the explicit personal-note command to submit chosen content as a new source record.

See `../../docs/SB2_SAFE_DEFAULTS.toml` for an all-OFF example and `../../docs/SB2_IMPLEMENTATION_AND_ACCEPTANCE.md` for exact source policies, commands, P00–P14 mapping and remaining acceptance gates. Do not paste a long-lived administrator token into a note or this repository.

## Build and tests

```sh
npm test
npm run check
npm run build
node --check dist/main.js
```

The bundle has no runtime npm dependencies. `dist/main.js`, `dist/manifest.json` and `dist/SHA256SUMS.json` are generated by `build.cjs`. Unit tests cover interrupted writes, complete/partial manifests, generation changes, paths, malicious content, user edits, withdrawal, paging and UI command registration. A successful build is not an actual Obsidian mobile API acceptance result.

## Server API

The API lives below `/api/life/v1/` on the existing Python server. Capture uses `events:batch` or approved export import. Timeline, event detail, scoped evidence, current/as-of recall, question responses, persisted briefings, relations, predictions/actuals, delivery state, projection manifest paging and view acknowledgements are separate interfaces. Reads never grant publication or administrator authority. A UUID or content hash is not a permission.

The server's projection snapshot is bounded, currently 10,000 candidate events and a bounded response. Timeline paging uses its separate query path. These bounds and a 300-question synthetic evaluation do not establish the plan's 100,000-event latency target or human semantic-search quality.

## Acceptance still required

Actual Mac/iPhone installation, native Phone History build/signing and share capture, foreground/offline/reconnection behavior on the real apps, and production TLS/notification channels need their own evidence. Health/location collection and notifications must not be turned on merely because the plugin built. Latest automatic results live in the source-bound verification report; old first-stage prose is not a current release verdict.
