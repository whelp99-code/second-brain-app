Second Brain, 쉽게 읽는 설명서

이 페이지는 개발을 모르는 사람도 읽을 수 있게 쓴 부분입니다. 명령어·설정·오류 코드 같은 기술적인 내용은 위쪽 “🛠 자세히 보기” 탭에 따로 모아 두었습니다.

1. 이게 대체 뭔가요

한 줄 요약

내 컴퓨터 안에만 사는 개인 서재입니다. 내가 넣은 자료의 원본은 절대 지우지 않고 보관하고, 그 원본을 근거로 정리된 “지식 페이지”를 만들어 줍니다.

서재에 비유하면 이렇습니다.

📦원본 보관함

내가 넣은 메모·파일의 원본 그대로를 창고에 넣어 둡니다. 한 번 들어간 원본은 사람이 명시적으로 승인하지 않는 한 지워지지 않습니다.

📚정리된 서가

창고의 자료를 주제별로 묶어 읽기 좋은 페이지로 만들어 서가에 꽂아 둡니다. 이 페이지가 평소에 읽고 검색하는 대상입니다.

🧑‍🏫사서

어느 페이지의 어느 문장이 창고의 어느 원본에서 왔는지 각주로 기록합니다. “이거 어디서 나온 말이야?”에 항상 답할 수 있습니다.

🗒️아침 브리핑

새로 들어온 게 있으면 그날의 요약 페이지를 하나 만들어 둡니다. 변화가 없는 날에는 만들지 않습니다.

중요한 점 하나. 이 서재는 내 컴퓨터(Ubuntu) 안에서만 열립니다. 웹 화면은 그 컴퓨터 자신(127.0.0.1, “나 자신”을 뜻하는 주소)에만 열려 있어서, 같은 네트워크의 다른 사람이 주소를 안다고 해서 들어올 수 있는 구조가 아닙니다.

이럴 때 씁니다
  • 회의·계약·결정 사항을 적어 두고 몇 달 뒤에 “그때 뭐라고 했더라”를 찾고 싶을 때
  • AI 비서(Claude Code·Codex·OmO)가 긴 대화 중에 앞부분을 잊어버려도, 중요한 사실은 계속 기억하게 하고 싶을 때
  • 정리본이 틀렸을 때 원본까지 거슬러 올라가서 확인하고 싶을 때

2. 어떤 문제를 풀어 주나요

메모 앱은 많습니다. 이 제품이 신경 쓰는 것은 딱 네 가지입니다.

① 원본 보존 — “요약본만 남고 원본이 사라지는 일”이 없게

보통의 자동 정리 도구는 요약을 만들고 나면 원본을 어딘가에 흘려버립니다. Second Brain은 넣은 자료의 바이트를 그대로 창고에 넣고, 내용으로 이름을 붙여 보관합니다(같은 내용이면 한 번만 저장됩니다). 청소 명령조차도 사람이 두 번 확인해야만 실제로 지웁니다.

② 출처 각주 — “근거 없는 문장”을 만들지 않게

정리된 페이지의 문장에는 각주가 붙습니다. 각주는 창고에 있는 원본을 가리킵니다. 각주가 가리키는 원본이 없어졌거나 각주가 깨져 있으면, 점검 명령(sb doctor)이 그것을 실패로 알려 줍니다. 즉 “출처 없는 문장이 조용히 섞여 있는 상태”가 유지될 수 없습니다.

③ 충돌 표시 — “어느 게 맞는지 몰래 고르지 않게”

“계약서는 수요일에 보낸다”와 “계약서는 금요일에 보낸다”가 둘 다 들어오면, 시스템은 몰래 하나를 고르지 않습니다. 충돌로 표시해 두고 사람에게 물어봅니다. 사람이 왼쪽/오른쪽 중 하나를 고르거나 메모를 남기면, 그 결정이 기록으로 남습니다.

④ 복구 가능성 — “되돌릴 수 있게”

매일 자동으로 백업을 만들고, 만든 직후에 그 백업을 실제로 풀어서 검사합니다. 검사에 통과하면 영수증 파일이 함께 남습니다. “백업은 돌고 있는데 정작 복구가 안 되는” 상황을 막기 위한 설계입니다.

주의

복구는 항상 새 폴더로 풉니다. 운영 중인 서재 위에 덮어쓰는 동작은 아예 거부됩니다. 덮어쓰기로 인한 사고가 원천적으로 불가능하도록 막아 둔 것입니다.

3. 하루가 이렇게 흘러갑니다

📝 메모를 넣는다→ 📦 원본 보관→ 📚 페이지로 정리→ 🗒️ 아침 브리핑→ 🤖 AI 비서가 꺼내 씀
  1. 넣는다 웹 화면의 “기억하기”에 한 줄 적거나, 파일을 끌어다 놓습니다. 이 순간에는 아직 정리되지 않습니다. 대기함(inbox)에 들어갑니다.
  2. 정리된다 1시간마다 자동으로 도는 작업이 대기함을 비우고, 원본을 창고에 넣고, 정리된 페이지를 만듭니다. 기다리기 싫으면 웹 화면의 “지금 처리” 버튼을 누르면 됩니다.
  3. 브리핑이 생긴다 새로 들어온 게 있거나 페이지가 새로 만들어진 날에만 그날의 브리핑이 만들어집니다. 조용한 날에는 브리핑이 없는 게 정상입니다. (아무 변화 없이 AI를 호출하지 않으려는 설계입니다.)
  4. AI가 꺼내 쓴다 Claude Code·Codex CLI·OmO에서 대화가 길어져 앞부분이 압축되는 순간, Second Brain이 “압축되면서 사라질 뻔한 사실”을 서재에서 찾아 다음 요청 앞에 붙여 줍니다.
  5. 백업된다 매일 새벽에 백업이 만들어지고, 만들자마자 검증됩니다.
한 줄 요약

넣기만 하면 나머지는 자동입니다. 사람이 직접 할 일은 충돌 해결과 신호등이 빨간불일 때의 조치 정도입니다.

4. 5분이면 쓸 수 있습니다

웹 브라우저에서 http://127.0.0.1:8765/ 를 엽니다. (이 주소는 “지금 이 컴퓨터”를 뜻합니다. 다른 컴퓨터에서는 열리지 않습니다.)

기억하기 — 한 줄 넣어 보기

  1. 화면의 기억하기 칸에 내용을 적습니다. 예: 계약서는 수요일에 발송한다.
  2. 제목은 선택입니다. 적어 두면 나중에 찾기 쉽습니다.
  3. 저장하면 “대기함에 들어갔다”는 응답이 옵니다. 아직 검색에는 안 잡힙니다.
  4. 바로 반영하고 싶으면 지금 처리을 누릅니다. 정리 작업이 한 번 돕니다.
주의

“저장했는데 검색이 안 돼요”의 거의 모든 원인이 이것입니다. 저장 = 대기함 접수, 검색 반영 = 정리 작업이 한 번 돈 뒤입니다.

파일 올리기

  • 웹 화면에 파일을 끌어다 놓으면 올라갑니다.
  • 파일 하나당 10MiB(약 1천만 바이트)까지입니다. 허용된 확장자만 받습니다.
  • 올라간 파일도 메모와 똑같이 대기함에 들어가고, 정리 작업이 돌 때 처리됩니다.
  • 맥을 쓴다면 별도의 메뉴바 앱으로 Finder에서 파일을 끌어다 놓거나, 지정한 폴더를 자동으로 서버에 동기화할 수 있습니다. (맥 폴더 동기화는 서버 방향 한쪽으로만 가고, 삭제는 전달하지 않습니다.)

검색하기

  • 검색창에 핵심 단어를 공백으로 띄워 적습니다. 예: 백업 검증 절차
  • 단어 순서는 상관없지만, 적은 단어가 전부 들어 있는 자료만 나옵니다.
  • 정확히 이 문구가 붙어 있어야 한다면 큰따옴표로 묶습니다. 예: 릴리스 "reader drain"
  • 자세한 요령은 5장에 따로 적었습니다. 이 부분은 꼭 읽어 두시는 편이 좋습니다.

충돌 해결하기

  1. 화면의 충돌 목록에 “서로 어긋나는 두 진술”이 올라옵니다.
  2. 둘 중 맞는 쪽을 고릅니다 — 왼쪽 유지(keep-left), 오른쪽 유지(keep-right), 또는 판단 보류하고 메모만 남기기(note).
  3. 메모를 함께 남길 수 있습니다. “계약 담당자가 금요일로 변경 통보” 같은 이유를 적어 두면 나중에 근거가 됩니다.
  4. 결정하면 그 자체가 기록으로 남습니다. 지워지는 것은 없습니다.
이럴 때

충돌을 방치해도 시스템이 임의로 고르지 않습니다. 서두를 필요는 없습니다. 다만 해결하지 않으면 두 진술이 모두 “미확정”으로 남아, 검색 결과에서 어느 쪽도 확정된 사실로 표시되지 않습니다.

5. 검색을 잘하는 법 (가장 중요한 장)

먼저 알아 두실 것

지금의 검색은 내가 적은 단어가 문서 안에 글자 그대로 들어 있어야 찾습니다. “~는”, “~에서”, “~인가요?” 같은 조사·어미·물음표가 붙으면 그 덩어리가 문서에 그대로 있을 수 없으므로, 자연스러운 한국어 질문은 대부분 결과가 0건으로 나옵니다. 이것은 고장이 아니라 현재 구현의 한계이고, 저희도 측정해서 알고 있습니다(자세히 보기 7·12장).

요령 하나: 조사를 빼고, 명사만 띄어서

이렇게 적으면 0건이렇게 바꾸면 찾습니다
백업은 어떻게 검증하나요?백업 검증
계약서를 언제 보내기로 했죠?계약서 발송
unified-db의 포트가 뭐였더라unified-db 포트
릴리스 전환 절차가 궁금해요릴리스 전환 절차

요령 둘: 붙어 있는 문구는 큰따옴표로

노을 "세 번 실패" 라고 적으면, 노을이라는 단어가 있고 세 번 실패라는 문구가 그대로 붙어 있는 자료만 찾습니다. 따옴표를 열고 닫지 않으면 오류가 납니다.

요령 셋: 단어를 너무 많이 넣지 않기

단어를 넣을수록 조건이 좁아집니다(전부 들어 있어야 함). 2~3개가 대체로 가장 잘 맞습니다. 안 나오면 단어를 빼면서 넓히세요. 단어를 더하는 건 좁히는 방향입니다.

한 줄 요약

검색은 문서에 있는 단어 그대로, 조사 빼고, 2~3개. 문장으로 묻지 마세요.

이럴 때

기억이 흐릿해서 단어가 안 떠오를 때는, 날짜로 좁힌 “최근 변경” 목록을 보거나 그날의 브리핑 페이지를 펼쳐 보는 편이 빠릅니다. 검색은 단어가 떠오를 때 쓰는 도구입니다.

6. AI 비서가 기억을 꺼내 쓰는 법

AI와 길게 대화하면, 대화가 너무 길어진 시점에 앞부분이 요약으로 압축됩니다(컴팩션). 이때 구체적인 숫자·날짜·결정이 뭉개지기 쉽습니다. Second Brain은 그 순간에 끼어들어, 압축된 요약에서 핵심 단어를 뽑아 서재를 검색하고, 찾은 사실을 다음 요청 바로 앞에 붙여 줍니다. 이 연결 장치를 “훅(hook)”이라고 부릅니다. 세 클라이언트 모두 같은 장치를 씁니다. 한 번에 최대 8개 기록, 전체 16KB 정도까지만 붙입니다(대화를 밀어내지 않기 위한 한도입니다).

Claude Code

Claude Code 설정에 세 가지 시점(프롬프트 제출, 압축 직후 세션 시작, 압축 완료)을 등록해 둡니다. 실제로 문맥이 그 턴 안에서 주입되는 시점은 “압축 직후 세션 시작” 하나뿐이고, “압축 완료” 시점에 붙이려 하면 Claude Code가 무시합니다(2.1.270 기준으로 실제 세션에서 확인된 동작). 그래서 Second Brain은 압축 완료 시점에는 조용히 다음에 쓸 재료만 챙겨 두고, 실제 주입은 세션 시작 쪽에서 합니다. 압축 요약이 비어 있는 경우도 있는데, 그때는 직전에 기억해 둔 “마지막으로 쓸모 있었던 검색어”로 대신 검색합니다.

Codex CLI

설정 파일 모양만 조금 다를 뿐, Claude Code와 똑같은 세 시점·같은 명령·같은 제한 시간(20초)을 씁니다. 다만 Codex에는 함정이 하나 있습니다. 훅 설정을 바꾼 뒤 처음 Codex 화면을 띄우면 “Hooks need review”가 뜨고, 사용자가 한 번 “Trust all and continue”를 눌러 줘야 훅이 켜집니다. 그전까지는 오류도 없이 그냥 조용히 아무 일도 일어나지 않습니다. “왜 기억을 못 꺼내지?” 싶으면 이걸 먼저 확인하세요.

OmO (senpi)

OmO에는 작은 확장 파일을 하나 설치합니다. 걸리는 시점은 두 개입니다 — 매 요청 직전(여기서 “마지막 검색어”를 갱신하고, 남겨 둔 문맥이 있으면 조용히 끼워 넣습니다)과 대화 압축이 실제로 수락된 순간(먼저 재료를 챙기고, 이어서 이번 턴에 바로 문맥을 밀어 넣습니다). 주입되는 메시지는 화면에 보이지 않게 처리됩니다. 이미 켜져 있는 OmO 세션은 다시 불러오거나 재시작해야 확장이 적용됩니다. 훅이 실패하거나 아무것도 못 찾으면 그냥 아무것도 붙이지 않습니다. 어떤 경우에도 AI 쪽이 죽지 않게 설계돼 있습니다.

한 줄 요약

훅은 “대화가 압축되는 순간, 서재에서 관련 사실을 꺼내 붙여 주는 장치”입니다. 잘 되면 티가 안 나고, 안 돼도 AI가 멈추지 않습니다.

7. 신호등(준비 상태) 읽는 법

시스템에는 두 종류의 상태 등이 있습니다. 하나는 맥박(/health) — 프로그램이 살아 있느냐만 봅니다. 다른 하나는 신호등(/ready) — “지금 믿고 써도 되느냐”를 봅니다. 우리가 봐야 할 것은 신호등 쪽입니다.

🟢 초록불 — ready

최근에 정리 작업이 성공했고, 검증된 백업이 있고, 밀린 요청이 없습니다. 그냥 쓰면 됩니다.

🟡 노란 기운 — 경고

점검 명령에서 “warn”이 몇 개 보이는 상태. 대체로 기능에는 영향이 없습니다. 예: 설치 방식 차이로 생기는 스케줄러 파일 경고.

🔴 빨간불 — 이유가 붙습니다

신호등이 빨간불이면 반드시 “왜”에 해당하는 코드가 함께 나옵니다. 코드를 보고 아래 표대로 대응하면 됩니다.

주의 — 이것만은 지켜 주세요

유지보수가 도는 동안에는 상태 조회나 검색을 같이 돌리지 마세요. 유지보수는 “지난 판본을 아무도 안 보고 있는지” 확인한 뒤에야 치우는데, 그 순간 누군가 파일을 열고 있으면 치우기가 실패합니다. 실제로 운영 중에 이 사고가 한 번 났고, 1분 뒤 혼자만 돌렸더니 정상적으로 끝났습니다.

8. 백업과 되돌리기

백업은 자동입니다

매일 새벽에 백업이 만들어집니다. 만들어진 직후에 실제로 임시 공간에 풀어서 체크섬·기록·각주를 검사하고, 통과하면 “검증됨” 영수증 파일을 남깁니다. 그래서 백업 파일 옆에는 늘 검증 기록이 하나 더 있습니다.

  • 백업에는 정리된 페이지와 원본 창고, 내부 기록이 들어갑니다.
  • 예전 프로그램 버전, 예전 백업, 관계없는 다른 파일은 들어가지 않습니다.
  • 검증에는 임시로 풀어 볼 디스크 여유 공간이 필요합니다.

되돌리기는 항상 “새 폴더로”

복구는 반드시 비어 있는 새 폴더로 풉니다. 운영 중인 서재를 가리키면 시스템이 거부합니다. 풀어 놓은 뒤 내용을 비교해 보고, 필요한 부분만 다시 넣는 방식이 안전합니다.

주의

다른 컴퓨터(다른 설치본)에서 만든 백업을 가져오면 “출처가 다르다”며 검증에 실패합니다. 이건 고장이 아니라, 남의 백업을 내 정상 상태의 근거로 쓰지 못하게 막는 장치입니다. 그런 백업도 새 폴더로 풀어 보는 것은 가능합니다.

프로그램 버전 되돌리기

프로그램은 버전별 폴더에 하나씩 쌓이고, “현재”라는 이름표 하나가 그중 하나를 가리킵니다. 새 버전으로 바꾸는 것도, 예전 버전으로 되돌리는 것도 이 이름표를 옮기는 것이 전부입니다. 예전 버전 폴더는 지우지 않으므로 되돌릴 자리가 늘 남아 있습니다.

참고: “저장된 지식”을 통째로 되돌리는 명령은 일부러 만들어 두지 않았습니다. 되돌리기는 ① 프로그램 이름표를 옮기거나 ② 백업을 새 폴더로 풀어 대조하는 두 가지 방법으로만 합니다.

9. 절대 하지 말 것

하지 말 것왜
유지보수가 도는 중에 검색·상태 조회를 같이 돌리기지난 판본 정리가 실패합니다. 유지보수는 혼자 돌려야 합니다.
운영 중인 서재 폴더 위로 백업 풀기시스템이 거부합니다. 반드시 새 폴더로 푸세요.
내부 기록 파일(데이터베이스)을 직접 열어 고치기“무엇이 언제 어떻게 바뀌었는지”를 증명하는 구조가 깨집니다. 실패 기록조차 감사 목적으로 보존합니다.
봉인된 판본 폴더의 권한을 임의로 바꾸기“읽기 전용으로 봉인됨”이 무결성 약속의 일부입니다.
설정 파일에 든 개인키 값을 복사하거나 화면에 출력하기비밀 자료입니다. 어디에도 붙여넣지 마세요.
충돌을 시스템이 알아서 고르게 하려고 시도하기그런 기능이 없습니다. 제품 원칙상 사람이 고릅니다.
승인 없이 원본 지우기청소 명령도 두 단계 확인이 있어야만 실제로 지웁니다.

10. 아직 못 하는 것 (정직하게)

  • 자연스러운 문장으로 검색하기. 측정해 보니 자연어 질문 66건, 의역 13건 모두 회수율 0이었습니다. 핵심 단어를 띄어서 넣는 방식만 잘 동작합니다(키워드 기준 0.74~0.82).
  • 의미 기반(비슷한 뜻) 검색. 기능 자체는 있지만 기본은 꺼져 있고, 켜더라도 다음 판본부터 적용됩니다. 이미 봉인된 판본은 설정만 바꿔서 다시 색인되지 않습니다.
  • 지난 브리핑 다시 만들기. 그날의 입력과 날짜를 고정해 재생할 수 없기 때문에 일부러 막아 두었습니다.
  • 조용한 날의 브리핑. 새로 들어온 게 없으면 브리핑을 만들지 않습니다.
  • AI 없이 동작하기. 페이지 정리·충돌 판정·브리핑은 모두 외부 AI 백엔드가 필요합니다. 그쪽 계정 한도나 설정 문제가 그대로 실패로 나타납니다.
  • 여러 사람이 나눠 쓰기. 한 사람·한 서재·한 명의 쓰기 담당자를 전제로 만들어졌습니다. 자료에 붙는 소유자/프로젝트 표시는 분류 기록일 뿐 접근 차단 장치가 아닙니다.
  • 개인정보 가리기. 가려지는 것은 자격증명 형태의 문자열(액세스 키, 토큰, 비밀번호, 인증서 등)뿐입니다. 이메일 주소나 전화번호는 그대로 남습니다.

11. 자주 묻는 질문

인터넷에 내 메모가 올라가나요?

웹 화면과 API는 그 컴퓨터 자신에게만 열려 있어서 외부에서 접속할 수 없습니다. 맥에서 쓸 때도 안전한 터널을 통해 “그 컴퓨터 안”으로 들어가는 방식을 권장합니다.

다만 페이지 정리·브리핑을 만들 때는 외부 AI 서비스를 호출합니다. 현재 운영 백엔드는 OmO를 거친 Grok입니다. 외부에 보내면 안 되는 자료는 그 자료원의 정책을 deny 또는 로컬 전용으로 설정해야 합니다.

저장했는데 검색에 안 나와요.

저장은 “대기함에 접수”까지입니다. 정리 작업이 한 번 돌아야 검색에 들어갑니다. 1시간마다 자동으로 돌지만, 급하면 웹 화면의 “지금 처리”을 누르세요.

그래도 안 나오면 검색어 문제일 가능성이 높습니다. 조사를 빼고 명사만 넣어 다시 시도해 보세요.

왜 질문처럼 검색하면 아무것도 안 나오죠?

현재 검색은 적은 단어가 문서에 글자 그대로 들어 있어야 찾습니다. “계약서를”은 문서에 “계약서”로만 있으므로 안 맞습니다. 조사·어미·물음표를 떼고 명사만 남기세요.

이건 알려진 한계이고, 고치려면 한국어 형태소 처리나 의미 검색을 붙여야 합니다. 로드맵 1순위입니다.

오늘 브리핑이 없어요. 고장인가요?

아닙니다. 새로 들어온 자료가 없고 새로 만들어진 페이지도 없는 날에는 브리핑을 만들지 않습니다. AI를 헛되이 호출하지 않으려는 설계입니다.

같은 내용을 두 번 넣으면 두 번 저장되나요?

원본 창고는 내용으로 이름을 붙이기 때문에, 완전히 같은 내용은 한 번만 저장됩니다. 또 이미 처리한 자료는 다시 처리하지 않도록 표시해 둡니다.

잘못 넣은 메모를 지울 수 있나요?

아직 정리되지 않은 대기함 항목은 화면에서 버릴 수 있습니다. 이미 정리된 페이지도 화면에서 “잊기”로 없앨 수 있고, 그 사실이 기록으로 남습니다.

다만 원본 창고의 바이트는 청소 명령을 사람이 두 단계로 승인해야만 실제로 사라집니다. 실수로 지워지지 않게 하려는 의도입니다.

“충돌”이 계속 쌓이는데 그냥 둬도 되나요?

둬도 시스템이 임의로 고르지 않으니 위험하지는 않습니다. 다만 해결되지 않은 동안 두 진술 모두 확정된 사실로 취급되지 않습니다. 시간 날 때 한 번에 정리하시면 됩니다.

AI 비서가 옛날 얘기를 반복해서 꺼내요.

훅은 이미 전달한 기록을 세션별 파일에 적어 두고 중복을 피합니다. 반복된다면 그 세션 파일이 사라졌거나 세션이 새로 시작된 경우입니다. 보통은 세션을 새로 시작하면 정리됩니다.

Codex에서 기억이 전혀 안 붙습니다.

거의 항상 신뢰 승인 문제입니다. Codex 화면을 한 번 띄우면 “Hooks need review”가 뜨는데, 여기서 “Trust all and continue”를 한 번 눌러 줘야 훅이 켜집니다. 그 전에는 오류도 없이 조용히 아무 일도 하지 않습니다.

웹 화면이 안 열려요.

웹 서비스가 떠 있는지 먼저 확인합니다. 주소가 이미 다른 프로그램에 점유돼 있으면 시작에 실패합니다. 살아 있는지만 보려면 /health, 믿고 써도 되는지 보려면 /ready를 확인합니다.

디스크가 얼마나 필요하죠?

원본 창고 + 정리된 페이지 + 백업 아카이브만큼입니다. 여기에 백업 검증용 임시 공간이 추가로 필요합니다. 검증은 실제로 풀어 보기 때문입니다.

업로드 크기 제한은요?

파일 하나당 10MiB입니다. 허용된 확장자만 받고, 경로를 조작하는 형태의 파일 이름은 거부합니다.

맥에서도 쓸 수 있나요?

네. macOS 14 이상용 메뉴바 앱이 있습니다. Finder에서 파일 드롭, 선택 폴더 자동 동기화, 알림 센터 브리핑, 검색을 제공합니다. 실제 동작은 Ubuntu 쪽 엔진이 하고, 맥 앱은 안전한 터널로 연결합니다.

“이거 어디서 나온 말이야?”를 어떻게 확인하죠?

정리된 페이지의 문장 끝에 각주 번호가 붙어 있습니다. 그 각주는 원본 창고의 특정 파일을 가리킵니다. 각주가 깨져 있으면 점검 명령이 실패로 알려 주기 때문에, 근거 없는 문장이 오래 남아 있을 수 없습니다.

실수로 뭔가 망가뜨렸을 때 제일 먼저 뭘 보면 되나요?

① 신호등(/ready)의 이유 코드, ② 점검 명령(sb doctor)의 실패 항목, ③ 상태 화면의 최근 단계 기록. 이 세 가지면 대부분 원인이 드러납니다. 자세한 대응표는 “자세히 보기 → 11 문제 해결”에 있습니다.

동작(스크립트 본문 기준):

  1. git rev-parse HEAD로 소스 커밋을 고정하고 git archive로 커밋된 트리만 임시 디렉터리에 푼다. 작업 트리의 미커밋·미추적 파일은 릴리스에 들어가지 않는다(working_tree_modified는 매니페스트에 기록만 된다).

  3. uv python find --managed-python --no-python-downloads --system 3.12로 찾은 런타임을 deploy/bundle_python_runtime.py가 릴리스 안으로 번들한다.
  4. 릴리스 ID는 휠 바이트 + requirements + 런타임 다이제스트 + 준비 레시피 해시로 계산한다(release_id_scheme: "sb-release-inputs-v3"). 같은 ID가 이미 있으면 에러로 중단한다.
  5. releases/<release_id>/ 아래에 .venv/, runtime/python/, 휠, requirements.txt, bin/{sb,second-brain-mcp,second-brain-agent-mcp}, release-manifest.json을 만든다. 디렉터리 모드 0700, 래퍼 스크립트 0700.
  6. 마지막 줄로 릴리스 디렉터리 경로를 출력한다.

5.1 공통 규칙

  • 진입점은 sb.cli:main. 인자가 하나도 없으면 도움말을 출력하고 종료 코드 2.
  • 모든 명령은 실행 후 Vault 루트가 디렉터리이면 메트릭(command, exit_code, 소요 ms)을 기록한다(sb/metrics.py: record_command). 기록 실패는 무시된다.

6.3 sb run 배치 규칙 (중요)

sb/pipeline.py: _run_all_mutable

1. 정체된 배치 정리(interrupt_stale_batches) + batch 행 'running' 기록
2. ingest 실행           → outcomes에 기록 → batch 진행 상황 갱신
3. compile 실행          → outcomes에 기록 → batch 진행 상황 갱신
4. if ingest.written == 0 and compiled.pages == 0:
       brief 를 실행하지 않는다
       (대신 compile 결과 또는 ingest 결과를 배치 결과로 재사용)
   else:
       brief 실행       → outcomes에 기록 → batch 진행 상황 갱신
5. _choose_batch_outcome(ingest, compiled, brief)

즉 brief는 수집이 무언가를 썼거나 컴파일이 페이지를 만들었을 때만 돈다. 아무 변화가 없는 시간당 실행은 LLM 호출 없이 끝난다.

_choose_batch_outcome의 우선순위:

  1. exit_code != 0인 첫 단계가 있으면 그 단계를 반환(가장 먼저 실패한 단계가 이긴다).
  2. status == "capped"인 단계가 있으면 그 단계를 후보로 잡는다.
  3. status == "partial"인 첫 단계가 있으면 그 단계를 반환. (나중 단계가 성공해도 앞 단계의 오류를 지우지 않는다.)
  4. 그렇지 않으면 brief 결과.

    • 그 행의 finished_at보다 나중에 끝난 done brief 행이 존재할 것 (_has_later_done_brief)

7.2 매칭 규칙 (이것이 한계의 근원이다)

LexicalQuery.predicate():

(instr(compact, ?) > 0 OR instr(normalize_id, ?) > 0 OR instr(normalize_section, ?) > 0)
AND … (모든 검색어에 대해 반복)

normalize(text) = casefold() 후 모든 공백 제거. 즉:

  • 질의는 공백으로 토큰 분리된다.

  • 형태소 분석·어간 추출·불용어 제거·동의어 확장은 없다.

순위(ordering()):

  • 토큰이 1개면 상대 빈도 기반 점수 내림차순.
  • 2개 이상이면 입력 문구 전체가 연속으로 들어간 결과를 먼저(CASE 0), 그다음 점수 순.

스테이지 스키마(_write_stage):

필드의미
session_id세션 식별자
event_digestsha256(session_id \0 occurrence_id \0 summary). occurrence_id는 prompt_id/compaction_id/event_id/uuid 등으로 구성

in_turn이번 턴에 주입한 레코드(확정 대기)

동작 흐름:

  1. UserPromptSubmit — 프롬프트로 _hook_search를 돌려 결과가 있으면 last_query를 그 검색어들로 갱신한다(_remember_last_query). 스테이지가 없거나 delivered: true면 아무것도 주입하지 않는다. 미전달 레코드가 있으면 context를 그대로 주입하고 pending_confirm을 세운다.
  2. PostCompact — 요약으로 검색해 레코드를 만든 뒤, delivered_in_turn에 이미 있는 것을 제외한다(_exclude_delivered). event_digest가 직전과 같으면 duplicate로 보고 스테이지를 다시 쓰지 않는다. 주입은 하지 않고 {}만 출력한다.
  3. SessionStart(source=compact) — 질의는 이벤트의 요약, 없으면 스테이지의 last_query를 쓴다. 둘 다 없으면 아무것도 하지 않는다. event_digest가 같고 이미 delivered면 중복으로 보고 건너뛴다. 검색 결과를 이번 턴에 바로 주입하고, 직전에 남아 있던 미전달 레코드 중 이번 턴 키와 겹치지 않는 것만 records(잔여)로 남긴다.
  4. confirm_delivery — CLI가 stdout 쓰기에 성공한 뒤에만 호출된다(sb/cli.py: postcompact_hook). in_turn에 있던 레코드 키를 delivered_in_turn에 합치고 in_turn을 비운다. 잔여가 없으면 delivered = true. stdout이 끊기면(BrokenPipe, 종료 코드 1) 전달로 기록하지 않는다.

검색 방식(_hook_search, _weighted_terms):

  • 요약에서 3자 이상, 불용어가 아닌 토큰을 빈도·식별자 성격(한글/CamelCase 우선)으로 정렬해 최대 32개 뽑는다(_candidate_tokens).
  • 각 토큰으로 limit = 8*4 = 32까지 검색한다. 결과가 0건이거나 32건 이상인 토큰은 버린다(너무 흔한 토큰 제거).
  • 남은 토큰의 가중치는 1/결과수. 페이지·섹션 단위로 가중치를 합산해 내림차순 정렬한다.
  • 6자 미만 토큰은 snippet에서 단어 경계로 정확히 일치할 때만 인정한다(_standalone_term).

레코드 선별(_matching_records): 히트 페이지의 .md를 읽어 parse_page_records로 기억 레코드를 쪼갠 뒤, 후보 검색어 중 하나라도 포함한 레코드만 고른다. 각 레코드에는 page_id, source_ref (프론트매터 sources 또는 각주 정의 [^sid]: origin에서 복원), record_id, version(레코드 다이제스트), snippet이 붙는다.

9.3 sb apply-requests --once

전제 조건(sb/cli_requests.py):

  • jarvis_public_keys가 비어 있지 않을 것
  • provider_signing_key_id와 provider_private_key가 설정돼 있을 것
  • 키가 base64url로 파싱될 것
  • 철회된 키(revoked_jarvis_signing_key_ids + <state_root>의 런타임 철회 파일)를 제외하고도 신뢰 키가 남아 있을 것

하나라도 어긋나면 REQUEST_EXECUTOR_KEY_CONFIG_INVALID + 종료 코드 1. scoped provider 설정이 잘못되면 SCOPED_PROVIDER_RUNTIME_CONFIG_INVALID + 1.

실행(RequestExecutor.apply_once, 기본 worker = "sb-apply-once", lease_ms = 60_000):

  1. mutations.maintain(observed) — 유지보수를 먼저 돌린다.
  2. _finalize_proved() — 이미 증명된 건 마무리.
  3. store.claim(...) — claim 실패 시 즉시 ApplyResult(None, "idle", None, "NO_PENDING_REQUEST", 0).
  4. 스키마 버전별 분기: 1/3(그리고 scoped authority가 있는 4)은 remember 경로, 2는 effect 경로.
  5. 결과를 prove로 확정.

출력은 정렬된 한 줄 JSON이다:

{"code":"NO_PENDING_REQUEST","fence":0,"phase":null,"request_id":null,"state":"idle"}

종료 코드: state가 idle / proved / reconciling이면 0, failed면 1.

9.6 scoped 쓰기 프로필

JARVIS가 MCP로 쓰기 요청만 보내는 전용 연결:

  • 이 설정에는 [mcp_scoped_read]를 넣지 않는다. [scoped_provider_verifier]가 필요하다.
  • 제공 도구는 sb_write_request(request) 하나다.
  • 응답은 수락 영수증이다. 실제 처리는 apply-requests --once가 하고, 완료 확인은 별도 scoped-record-read-v5 연결로 한다.
  • 오류나 연결 종료만으로 미수락을 단정하고 재전송하면 안 된다(README 경고).

10.2 LLM 백엔드

현재 운영 백엔드는 CLI argv 템플릿 하나다:

"llm" = {"argv_template" = ["/home/jm/.config/second-brain/llm/omo-grok.sh"]}

~/.config/second-brain/llm/omo-grok.sh:

#!/bin/sh
# second-brain LLM backend: Grok via OmO print mode (xAI OAuth held by OmO).
# Prompt arrives on stdin; the reply is printed on stdout (sb extracts the first JSON object).
export PATH="/home/jm/.nvm/versions/node/v24.19.0/bin:$HOME/.local/bin:/usr/local/bin:/usr/bin:/bin"
cd "$HOME/.local/state/second-brain/llm-cwd" || exit 1
MODEL="${SB_LLM_MODEL:-xai/grok-4.6}"
THINK="${SB_LLM_THINKING:-low}"
exec omo -p -nt -ne --no-session --model "$MODEL" --thinking "$THINK" \
  --system-prompt "…precise text-processing backend… output only the JSON object…" \
  2>/dev/null

동작 요점:

  • 템플릿에 {prompt}가 없으므로 프롬프트는 stdin으로 들어간다(§4.3).
  • stderr는 버리고 stdout만 쓴다. json_mode에서는 SB가 첫 JSON 객체를 뽑는다.
  • SB_LLM_MODEL, SB_LLM_THINKING 환경변수로 모델·추론 강도를 바꿀 수 있다(스크립트 자체 규약).

이전 백엔드는 격리된 CODEX_HOME을 쓰는 codex exec였다. 2026-09-15 기록에 따르면 사용자 ~/.codex/config.toml(로컬 프록시를 가리키는 openai_base_url)을 서비스가 상속해 모든 compile 호출이 실패했고, /home/jm/.local/state/second-brain/codex-home(0700, 빈 config + auth.json 심링크)을 만들고 argv_template 앞에 env CODEX_HOME=<그 경로>를 붙여 해결했다.

백엔드 교체 절차:

# 1) 새 백엔드 스크립트를 만든다 (stdin으로 프롬프트, stdout으로 답, 종료 코드 0)
install -m 0700 /dev/stdin ~/.config/second-brain/llm/my-backend.sh <<'EOF'
#!/bin/sh
exec my-llm-cli --quiet
EOF

# 2) 백업 후 두 설정 파일의 [llm].argv_template 를 바꾼다
cp ~/.config/second-brain/config.toml          ~/.config/second-brain/config.toml.bak-$(date +%Y%m%dT%H%M%S)
cp ~/.config/second-brain/jarvis-provider.toml ~/.config/second-brain/jarvis-provider.toml.bak-$(date +%Y%m%dT%H%M%S)
# "llm" = {"argv_template" = ["/home/me/.config/second-brain/llm/my-backend.sh"]}

# 3) 확인
sb doctor            # llm-cli 체크가 pass 인지
sb compile --dry-run # 상태만 읽는다(쓰기 없음)

교체 시 확인할 것:

  • argv_template[0]이 PATH 또는 절대 경로로 실행 가능해야 한다. 아니면 sb doctor의 llm-cli가 warn이고, 실제 호출은 command not found: <argv0>로 LLMUnavailable이 된다.
  • {prompt}를 argv에 넣으면 stdin 전달이 아니라 argv 치환 방식이 된다. 긴 프롬프트에는 stdin 방식이 안전하다.
  • model_id / prompt_version을 바꾸면 파생 키가 달라져 기존 페이지가 다시 컴파일된다. 비용과 LLM 호출 상한(caps.max_llm_calls_compile)을 함께 검토한다.
  • 백엔드가 외부 제공자로 바뀌면 데이터 제공자가 바뀌는 것이므로 사용자 승인 사안이다.
  • 두 설정 파일(config.toml, jarvis-provider.toml) 모두 바꿔야 한다. refresh 경로는 후자를 쓴다.

10.4 백업과 복원

백업 생성

sb backup                                   # <backup_root>/second-brain-<YYYYmmddTHHMMSS±ZZZZ>.tar.gz
sb backup /path/to/explicit-name.tar.gz

관리형 배치에서 backup_runtime은 세 겹의 락을 동시에 잡는다:

  1. request_root/pending 디렉터리 flock(LOCK_EX)
  2. 세대 저장소 exclusive() writer mutex
  3. 요청 저널의 BEGIN IMMEDIATE (끝나면 rollback)

그 상태에서 활성 세대 트리를 복사하고, 복사본 안의 .recovery/에 제어 저널만 담는다:

  • state: state_root의 1단계 *.db 파일
  • requests: request_root 전체 트리의 파일 (단 -wal, -shm, .lock, .tmp 제외)
  • .db/.sqlite는 SQLite backup() API로 복사한다(WAL 포함). 그 외는 바이트 복사.
  • 오래된 릴리스, 과거 백업, 무관한 호스트 파일은 들어가지 않는다.

출력 JSON: archive, checksum, verification, files, bytes.

검증

sb backup은 생성 직후 verify_runtime_backup을 호출한다. 검증은 임시 저장소로 복원해 체크섬·원장·인용을 검사하고 *.tar.gz.verified.json 영수증을 남긴다. 임시 저장소는 검사 후 제거되지만 복원용 추가 디스크 공간이 필요하다.

관리형 검증은 origin이 provider:<provider_instance_id>인지, tombstone high-water가 현재와 같은지 확인한다. 다르면 BACKUP_TOMBSTONE_OR_PROVIDER_MISMATCH. 제어 저널이 초기화돼 있지 않으면 backup verification requires initialized control journals.

출처가 없는 옛 백업은 준비 상태의 정상 근거로 쓰이지 않는다 — 새 백업을 만들어 검증한다.

sb verify-backup ~/.local/state/second-brain/backups/second-brain-20260915T184120+0900.tar.gz

복원

sb restore <archive> --to /absolute/new/restore-dir
sb restore <archive> --to /absolute/new/restore-dir --force
  • 목적지가 심링크이거나, 목적지가 활성 vault_root와 같고 설정에 share_root가 있으면 RESTORE_REQUIRES_ISOLATED_DESTINATION: use --to with a new directory로 거절한다. 운영 Vault 위에 덮어쓸 수 없다.
  • 복원은 사이드카 검증 → 배타 락 → 임시 디렉터리에 매니페스트 기준 전수 검증(경로 정규화, 중복 경로 거부, 파일 수 상한) → 원자 교체 순서다.
  • 복원 예산 상수(sb/restore.py): 멤버 100,000개, 파일당 64 MiB, 합계 10 GiB. 넘으면 RESTORE_ARCHIVE_BUDGET_EXCEEDED.
  • 출력 JSON: destination, files, bytes, previous.

복원 작업공간 정리

sb maintain --once --restore-workspace /absolute/private/restore-work

sanitizer에 넘긴 것과 같은 0700 폴더를 명시해야 한다. 진행 중인 복원은 기다리지 않고 restore_workspace_busy: true로 보고한다. 잠금을 쓰지 않는 구버전 복원 writer가 종료된 것을 확인한 뒤에만 쓴다. 기본 운영 타이머에 이 경로를 자동으로 추가하지 않는다.

13 알려진 한계와 로드맵

13.1 검색

  • 자연어 질의 0.0 — §7.7. 형태소 분석·n-gram 색인·의미 검색 중 하나가 필요하다. 데이터셋 수정으로는 해결되지 않는다.
  • 의미 검색은 기본 꺼짐 — [search] hybrid = true로 켜도 다음 관리형 세대부터 벡터가 봉인된다. 이미 봉인된 세대는 설정 변경만으로 재색인되지 않는다. 모델이 없거나 맞지 않으면 일반 검색을 유지한다.
  • MCP 검색은 레코드 AND — 모든 검색어가 같은 인용 레코드 안에 있어야 한다. CLI보다 좁다.
  • stale_decision 배제는 증명되지 않았다 — 해당 2건은 정답도 못 찾았으므로 0.0을 “잘 배제했다”로 읽으면 안 된다.

13.2 파이프라인

  • 과거 브리핑 재시도 불가 — BRIEF_REPLAY_INPUTS_UNAVAILABLE. 실패 행과 attempts는 감사 기록으로 보존된다. maintain의 supersede는 “이후 성공 brief 존재 + 일시적 LLM 오류 아님”일 때만 상태를 닫는다.
  • sb rollback 미구현 — 항상 ROLLBACK_REQUIRES_GENERATION_AUTHORITY. 실질 롤백은 릴리스 current 되돌리기 또는 백업 격리 복원이다.
  • brief는 변화가 있을 때만 실행 — 조용한 날에는 일일 브리핑이 생기지 않는다(§6.3).
  • LLM 의존 — compile/conflict/brief 모두 외부 CLI 백엔드가 필요하다. 백엔드 계정 한도·프록시 설정 같은 외부 조건이 그대로 실패로 나타난다.

13.3 접근 제어

  • [source_access]는 분류 기록이며 MCP/API 접근 제어가 아니다. 접근 claim·record/page 분류 결합과 범위 검사가 연결되기 전까지 기존 owner 프로필의 조회 범위는 그대로다(README).
  • scoped 연결은 semantic/hybrid 검색·쓰기·status·export·restore, 운영 권한 공급자, 다중 사용자 인증에 아직 연결돼 있지 않다.
  • 비밀 마스킹은 자격증명 정규식만이다(AWS 키, ghp_/gho_, sk-, PEM, password=/token=). 연락처 이메일·전화번호는 그대로 남는다(AGENTS.md).

13.4 운영

  • sb web의 CLI 인자가 [web] host/port보다 우선한다. 설정만 바꿔서는 바인딩이 바뀌지 않는다.
  • macOS 앱의 AppKit/SwiftUI/Notification Center/Keychain/ServiceManagement 실런타임 인수는 Xcode가 설치된 macOS에서만 완료할 수 있다. Ubuntu 자동 검증은 소스·API·보안 계약만 본다.

tombstone삭제 이력 레코드. set_root/sequence가 high-water를 이룬다. 재유입 차단과 백업 검증에 쓰인다
request journal (요청 저널)request_root/journal.db. JARVIS memreq의 상태 기계
memreqJARVIS가 SB에 보내는 서명된 기억 요청
fence요청 lease의 단조 증가 토큰. 오래된 소유자의 쓰기를 막는다
read_fence / access_claimscoped MCP 조회에 요구되는 서명된 범위 증명
releaseapp/releases/<release_id>. 커밋된 HEAD를 번들 런타임과 함께 봉인한 배포 단위
currentapp/current 심링크. 활성 릴리스를 가리키는 유일한 전환 지점
providerSB 인스턴스의 대외 신원(provider_instance_id, provider_release_sha, 서명키)
readiness/ready가 반환하는 운영 준비도. /health(프로세스 생존)와 다르다
stage 파일기억 훅의 세션별 상태 파일. <state_root>/.sb/session-memory/<session>.json

knowledge_status / approval_status지식 레지스트리의 상태. ACTIVE+APPROVED면 CANONICAL/VERIFIED, 그 외는 REFERENCE/UNVERIFIED
scope검색 범위. active(승인된 활성만), candidate, reference(=all, 상태 필터 없음)
capped예산 상한에 걸려 일부만 처리한 실행 상태. readiness상 성공으로 친다
